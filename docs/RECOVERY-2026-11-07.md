## 2. 今天查明的关键事实（非常重要）

### 2.1 启动链（Android 12+ 分体式）
```
ABL → boot.img(kernel=shim) → vendor_boot.img(ramdisk=payload, dtb=真实设备树)
       ↑ v4 头                                    ↑ shim 从 /chosen 读 initrd
```

### 2.2 **ABL 只接受 header_version 4**
v2 镜像刷进去 ABL 静默拒绝（回 fastboot，屏幕无任何信息）。这是卡了一整晚的根因。
- v4 头：`header_size=4096`、magic 后 0x08=kernel_size、0x0c=ramdisk_size、0x10=os_version、0x14=header_size、0x28=header_version、0x2c=cmdline[1536]
- 布局：header(4096) + kernel + ramdisk（各按 4096 对齐）

### 2.3 payload 必须放 vendor_boot 的 ramdisk
放 boot.img 的 ramdisk 里 shim 读不到（initrd 大小对不上，`no NABUXNU payload`）。

### 2.4 槽位"不可启动"是 AVB 决定的
- 刷官方（签名）镜像 → `slot-unbootable: no`
- 刷自制镜像 → 变 `yes`
- 解决：`fastboot --disable-verity --disable-verification flash vbmeta_a stock/vbmeta.img`

### 2.5 payload 的内存字段必须由原版 mkpayload 填
我们仓库 `qemu/mkpayload.py` 不填 `phys_base`/`mem_size`（全 0），shim 会打印
`PHYS size=00000000` 并报 `ramdisk overlaps kernel memory`。
原版 `ref-tools/mkpayload.py` 从 ADT 的 `/chosen` 读 `dram-base`/`dram-size` → `0x80000000` / `0x300000000`。

### 2.6 shim 的重叠检查要用 kernel_end，不是 mem_size
`loader.c` 原来用 `phys_base + mem_size`（12 GB）判断，任何 ABL 放在 DRAM 里的 initrd 都会误报。
改成 `phys_base .. kernel_end_pa`。

### 2.7 这个文本控制台没有滚动
`console.c` 的 `row` 一直加，超出屏幕的 `put_glyph` 直接 return。
**日志打多了不会卡死，但会看不见**——排查时要用固定坐标 `con_text_at()` 或色块。

## 9. 2026-11-06 04:15 —— GPU 固件到位 + GMU 路线确定

- shim 直写 GX GDSCR（0x2C9100C）：**CX 关闭时冻死**；**CX 打开后仍然冻死**

## 15. 2026-11-06 05:30 —— GPU 时钟全部打通（顺序是关键）

### 破解点：**CX 必须先上电，时钟才能开**

shim 实测：

```
开机时 CX GDSCR = 0x00222001（关闭）
若先开时钟 → GPUCC 三个分支全部起不来（读回 0x80000001，CLK_OFF 置位）
若先给 CX 上电（0x00222001 → 0xF8222000）→ 再开时钟 → 全部成功
```

### 实测成功的时钟（boot-gmutest6/7.img）

| 时钟 | 结果 |
|---|---|
| gcc_gpu_cfg_ahb_clk（0x71004） | ✅ 00000001 |
| gcc_gpu_memnoc_gfx_clk（**0x7100c**） | ✅ 00000221（之前写成 0x7110c 是错的）|
| gcc_ddrss_gpu_axi_clk（0x71154） | ✅ 00000001 |
| gpu_cc_ahb_clk（0x1078） | ✅ 00000001 |
| gpu_cc_cx_gmu_clk（0x1098） | ✅ 00004221 |
| gpu_cc_cxo_clk（0x109c） | ✅ 00000001 |
| **CLOCKS all_on** | ✅ **1** |

**结论：从 shim 里把 GPU 的时钟全部打开是可行的。**

### 仍未打通：GMU 寄存器访问

```
GMU sysreset 写 1 → 读回 0（写不进去）
写第一个固件块（ITCM addr=0）→ 整机卡住
```

已尝试：
- 配置 gmu_clk_src 的 RCG（0x1120/0x1124）→ cfg 本来就是 0x1（TCXO/1），更新成功，但无效
- 等手段（800 ms）→ 无效
- 确认写寄存器本身是生效的（往 CBCR 写 0 能读回 0）

**推断**：GMU 块还需要额外的电源/控制位（候选：
`GPU_CC_CX_GDSC` 的 `gds_hw_ctrl`(0x1540) 切成软件控制、
`gpu_cc_pll1`(0x100) 使能、
CX_MISC 里的 GMU 电源位），
或者必须由内核在完整平台初始化之后访问。

### 新增/修正的工具与事实
- shim 里 `clk_on()`：读-改-写 + 轮询 bit31，返回是否真的跑起来
- GCC memnoc CBCR 正确偏移是 **0x7100c**（不是 0x7110c）
- GPLL0 使能寄存器：GCC 基址 + 0x52000，bit0
- GPUCC 寄存器表里的数字是**字节偏移**，不能再乘 4
- gmu_clk_src RCG：cmd 0x1120（bit0=UPDATE），cfg 0x1124（bit8-10=源，bit0-7=分频）

## 16. 2026-11-06 05:45 —— GMU 寄存器分区定位

### 关键发现：GMU 寄存器分两个区，一个能读一个会挂

| 寄存器 | 偏移 | 实测 |
|---|---|---|
| CM3_SYSRESET | 0x1f800 | ✅ 可读（返回 0）|
| CM3_FW_INIT_RESULT | 0x1f81c | ✅ 可读（返回 0）|
| HFI_CTRL_INIT | 0x1f986 | 未单独测（同区，推测可读）|
| **CORE_FW_VERSION** | **0x1d3f8** | ❌ **读它整机挂死** |

→ 外层"包装"寄存器可访问，**CM3 核心区寄存器访问即挂**
→ 说明 **CM3 核心时钟/电源没起来**，不是总线地址问题

### 至此确认的 GPU 状态
```
✅ CX 供电轨（软件可控，0x222001 → 0xF8222000）
✅ GPUCC 时钟：ahb / cx_gmu / cxo 全部实测打开
✅ GCC 时钟：cfg_ahb / memnoc(0x7100c) / axi 全部打开
✅ GPLL0 使能
✅ GMU 外层寄存器可读
❌ CM3 核心未运行（核心区寄存器访问挂死）
❌ 固件无法写入 ITCM（写第一块就挂）
```

### 下一步靶子
让 CM3 核心时钟运行。候选：
1. `gpu_cc_pll1`（GPUCC 偏移 0x100，trion 类型 PLL）需要配 VCO 并使能 → 500 MHz
2. 之后 RCG `gpu_cc_gmu_clk_src`（0x1120/0x1124）的源切到 PLL1 而不是 TCXO
3. 或者 CM3 还需要额外的 "GMU core" 电源位（kgsl 的 gmu_core_power_up 里有）

**建议在内核里做**（内核有完整平台初始化），shim 里手工配 PLL 链成本过高
（每个寄存器写错都是挂死级别的调试）。

## 18. 2026-11-07 —— GPU 时钟打通 + 编译链路重建 + 黑屏定位

### 18.1 GPU：找到"时钟打不开"的真正原因

**症状**：GPUCC 的 3 个时钟分支写 enable 后，读回一直是 `0x80000001`（bit31 = CLK_OFF 置位），
时钟根本没跑，导致 GMU 寄存器写不进去。

**根因**：**顺序错了**。GPUCC 的时钟分支位于 CX 电源域内，
必须**先让 CX 上电**（GDSCR `0x222001 → 0xF8222000`），再使能时钟分支。

**实测（内核 probe=6）**：

| 时钟 | 修复前 | 修复后 |
|---|---|---|
| gpu_cc_ahb (0x1078) | 0x80000001 | **0x1** |
| gpu_cc_cx_gmu (0x1098) | 0x80004221 | **0x4221** |
| gpu_cc_cxo (0x109c) | 0x80000001 | **0x1** |

修法：`nabu_gpu_steps()` 内部固定按"时钟→投票→CX"执行，
所以改成**分两次调用**：先 `ARC|CX_GDSC`，再 `CLOCKS`。

### 18.2 GPU：仍然没通的部分

```
GMU 的 CM3 核心：寄存器访问会挂死（读 0x1d3f8 直接冻住）
→ 内核 probe=6 也卡在同一处（不是 shim 的问题）
→ 需要研究高通的 GMU 上电序列（PLL1 / gds_hw_ctrl / 电源域）
GX 供电：由 GMU 控制，CPU 写会冻机
AGX 驱动：仍是占位（不会真的画图）
```

### 18.5 黑屏：定位到用户态崩溃

**现象**：内核完整启动 → launchd 起来 → 然后 panic：
```
panic(...): launchd_cache_loader[22] exited -- exit reason namespace 7 code 1
```
（namespace 7 = OS_REASON_DYLD）

**已排除**：
- GPU（backboardd 一直在送帧，与 GPU 无关）
- 显示驱动（AppleCLCD 1600x2560 stride 6400 全部验证过）
- 代码签名（已修，launchd 能活）

**在查**：
1. 加补丁打印完整 dyld 错误（`NABU EXIT DESC`）
2. 加补丁在根分区挂载后检查 5 个关键文件（`NABU CACHE: OK/MISS`）：
   - /System/Library/Caches/com.apple.dyld/dyld_shared_cache_arm64e
   - /System/Library/dyld/dyld_shared_cache_arm64e
   - /usr/lib/dyld
   - /sbin/launchd
   - /System/Library/Caches/com.apple.dyld

**怀疑**：共享缓存 2-3 GB 的单文件，非日志式 HFS 可能读不了/映射不了。

### 18.6 重要教训：日志环记录不到早期日志

```
日志环要等 UFS + 根分区初始化之后才开始记录
而 GPU 探测在 EARLY_BOOT（之前）
→ NABU GMU 的输出永远进不了日志环
→ 只能用 panic 或屏幕直接看
```
